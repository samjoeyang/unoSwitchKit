## CI 第三个 bug：Apple 签名变量空串导致 Tauri 进入 security import 失败（2026-10-31）
- 现象：build.yml 第二次构建（run 41183513200）编译/链接已通过（mkdir 修复生效），但步骤 9 `build-release.sh --universal` 在**打包 codesign 阶段**报：
  `failed to run command security import -f pkcs12: failed to import the signing certificate as a PKCS#12 (.p12) file...`
- 根因：build.yml 顶层 env 把 `APPLE_CERTIFICATE` 等显式设成 `${{ secrets.APPLE_CERTIFICATE }}`，secret 不存在时解析为**空串而非未设置**。Tauri 打包器见 `APPLE_CERTIFICATE` 变量存在（即使空）就进入「导入 p12」分支，拿空串当证书解析 → 报错。原以为只 unset `APPLE_SIGNING_IDENTITY` 就够了，但 `APPLE_CERTIFICATE` 空串同样触发。
- 修复：build.yml 移除顶层 env 的 6 个 APPLE_* 声明，改为新增「准备签名环境」步骤——仅在 secret 真实非空时 `echo "$v=$val" >> $GITHUB_ENV`，空值一律不写入（Tauri 随之走 ad-hoc 自签）。build-release.sh 兜底：无证书时 `unset` 整组 Apple 变量（而非留空串）。
- 已提交并推送（cfc04bb）。第三次构建 run 41184290339 重新触发，由 post_build_release.sh（task aktU61）等待完成后建 Release。
- 经验：GitHub Actions 引用不存在的 secret 得到的是**空字符串**；任何把空串当「有值」消费的工具（Tauri 的 security import）都会踩坑——务必「非空才注入」。

## 【更正】「原生守护不亮」真正根因（2026-10-31 深夜，推翻上面 73-77 行结论）
