## 关键补充：下载的包（CI/邮件/Release）守护仍不亮 = Gatekeeper 隔离拦截

- 现象（用户复测）：本地/dev 构建能点亮 9876，但 **Actions 构建的包下载安装后守护仍不亮**。
- 根因（与 Tailscale/代码无关，是分发层问题）：CI 与本地都**无 Developer ID 证书 → ad-hoc 自签名**（已确认本地钥匙串无 Developer ID）。下载的 app 被系统打上 `com.apple.quarantine`，Gatekeeper 拦截其中**被 spawn 的 sidecar 守护进程**的 socket bind → 9876 长期 CLOSED → 状态点不亮。dev/就地构建不带隔离属性，故正常。
- 已实测复现：带 `com.apple.quarantine` 的守护进程能启动但 9876 CLOSED；去掉隔离的干净副本 9876 OPEN（log: `sidecar: listening on 127.0.0.1:9876`）。沙箱内 Gatekeeper 评估缓存会"记仇"（去隔离后仍拒），真实 Mac 靠用户右键「打开」批准可清。
- 解法：
  1. 用户侧临时：解压后 `xattr -dr com.apple.quarantine SwitchKit.app` + 首次右键「打开」批准主程序（每次重下载需重做）。
  2. 正规分发：**CI 用 Developer ID 签名 + 公证**。workflow/build-release.sh 已支持 `APPLE_*` 环境变量，只需在仓库 Secrets 加 `APPLE_CERTIFICATE`/`APPLE_CERTIFICATE_PASSWORD`/`APPLE_SIGNING_IDENTITY`/`APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` 即可开启签名+公证；tauri.conf.json 当前无显式 signing/notarization 配置（Tauri v2 靠环境变量驱动）。
- ⚠️ 教训：发邮件的包同样经下载会被隔离，BSD-socket 修复只解决了 Tailscale 层，没解决 Gatekeeper 层；要"下载即亮"必须公证（或有凭证的 Developer ID 签名）。

### 无证书解法（已落地，commit `6a52bf0`）
- 用户暂无 Developer ID 证书计划 → 在代码层解决：App 拉起守护前，把 `switchkit-daemon` **复制到 `/tmp/switchkit-daemon` 并 `xattr -d com.apple.quarantine` 去隔离，再从 /tmp 副本 spawn**（`src/main.rs` 的 `prepare_daemon_macos`/`strip_quarantine`，`#[cfg(target_os="macos")]`）。Rust `std::fs::copy` 本就不携带 xattr，再显式清一次兜底。
- 已实测：从带隔离的 app 包取出的守护→带 quarantine；复制到 /tmp 去隔离后→9876 OPEN（log `sidecar: listening on 127.0.0.1:9876`）。即下载包**无需证书、无需用户手动 xattr** 即可点亮。
- 注意：主程序本身仍需用户首次右键「打开」批准（ad-hoc 固有），但守护这一步已自动处理。本地 commit `6a52bf0`（未 push，需用户确认才推）。

- 用户明确：Tailscale(BSD socket) 与 Gatekeeper(复制/tmp去隔离) 两次归因都错；线索是「只要 Actions 自动构建的包就失败，本地能亮」→ 要查 CI 流程相对本地多/少了什么。
- 实证方法：下载 CI v0.4.3 universal/aarch64 包解压，与**本机同 commit 跑 `build-release.sh --universal`(Swift 5.7.2/Xcode14.2，等同用户本地能用的构建)** 的产物逐文件 diff。
- **用户纠正（关键）**：同一台 M 系列 Mac 上，**dev 构建(本地 Xcode 14.2/Swift 5.7.2)能点亮，Actions 构建(Xcode 26/Swift 6)不能点亮**。所以差异不是架构分片（两次前误判），而是纯构建环境差异。用户系统为 **macOS 27**。
- **已排除的假设**：① 架构(arm64/x86_64)——同一台 M 机器两者都跑 arm64，本地能、CI 不能；② quarantine/Gatekeeper——`prepare_daemon_macos()` 的复制+strip quarantine 兜底在本地与 CI 是同一份源码，不是 Actions 增减项；③ OTA 注入——仅改主程序 updater 配置，对守护签名范围无影响(CodeResources 行数本地/CI 都是 137、Info.plist 无差异)；④ "系统 Swift 运行时太旧"——macOS 27 自带 ≥ Swift 6 运行时，dyld 版本不匹配不成立。
- **实测反证（守护二进制本身没坏）**：在本机(Intel macOS 12.7.6)实跑 CI 包 x86_64 切片，`bind 9876` 成功（日志 `sidecar: listening on 127.0.0.1:9876`）。故 CI 守护产物可加载可监听；在用户 M 机器上起不来属 **Swift 6 在特定运行时环境的运行时行为差异**（具体崩点未在本机复现，因沙箱是 Intel 12.7.6 + 仅 Swift 5.7）。
- **根因结论**：Actions 相对 dev 唯一能动守护的实质差异 = **Swift 工具链**（Xcode 26/Swift 6 vs Xcode 14.2/Swift 5.7.2）。`build-release.sh` 的 `swiftc` 命令两处逐字相同，唯一变量是 `swiftc` 来自哪个工具链（`macos-latest` 当前为 Xcode 26/Swift 6）。
