## 守护不亮根因的二次修正（重要）

- 之前（11-01）结论是「Swift 6 vs dev Swift 5.7.2 工具链差异」。现据实证修正：
  - **Swift 6 守护二进制本身可运行**：在本机 Intel macOS 12.7.6 实测 CI 的 Swift 6 守护 x86_64 切片能 `bind 9876`；目标机 macOS 27 自带 ≥ Swift 6 运行时，dyld 不缺库。故 Swift 版本不是崩因。
  - **dev 包能亮、CI 包（GitHub 下载）不亮 → 指向 Gatekeeper/quarantine**。原 `prepare_daemon_macos` 把守护复制到 `/tmp` 去隔离再 spawn；但用户右键打开 app 后整个 bundle 的 quarantine 已清，**bundle 内守护本就能跑**，而 macOS 26+ 对脱离 app bundle 的 `/tmp` 副本（即使去隔离）反而更严、易被 AMFI 拦——这正是 0.4.1~0..3 下载包一直不亮的真因（方向对＝quarantine，但实现反了＝该优先 bundle 内）。
- **修复（src-tauri/src/main.rs）**：新增 `try_spawn_daemon`（spawn 后探测 9876 就绪 ~1s）；`spawn_sidecar` 翻转优先级——**先 spawn bundle 内守护，9876 探测失败再回退 `/tmp` 去隔离方案**。`cargo check` 已通过。

## 原生守护 Apple 芯片不亮（macOS 26+）根因与修复
- 现象：Actions 自动构建的 ad-hoc 包，Intel 上原生守护可点亮，Apple 芯片(macOS26/27)不亮。
- 根因：ad-hoc 包带 quarantine；用户"右键打开"只清 .app 顶层隔离，bundle 内 `switchkit-daemon` 是独立 Mach-O(ad-hoc 哈希不同)。Apple Silicon 有 AMFI，把嵌套隔离 ad-hoc 二进制当新隔离程序拦截 → spawn 失败 → 9876 起不来 → 不亮；Intel 无 AMFI 故亮。/tmp 去隔离 fallback 在 macOS26+ 也被 AMFI 拦。
- 修复(main.rs, commit d963d7a)：spawn bundle 内守护前先 `strip_quarantine` 清嵌套隔离；fallback 从 /tmp 改到 `~/Library/Application Support/com.switchkit.app/`。xattr 不计入代码签名哈希，删隔离不破坏签名。`cargo check` 通过。
- 旁证：`binaries/switchkit-daemon-x86_64` 本地副本"not signed at all"（Intel 容忍未签名，Apple 芯片不容忍）。
- 长期正解：配 Developer ID + 公证(docs/构建指南.md §6)，CI 经 APPLE_* secret 自动走。
