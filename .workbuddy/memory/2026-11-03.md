## CI 触发机制（重要坑）
- `build.yml` 是 `workflow_dispatch` **手动触发**，push 不会自动构建。必须去 Actions 页点 Run workflow，或用 API 触发。
- 本机用 GitHub API 触发成功：POST `https://api.github.com/repos/samjoeyang/unoSwitchKit/actions/workflows/build.yml/dispatches` body `{"ref":"main"}`。
- 取 token 的坑：`security find-internet-password -s github.com -w` 在沙箱非交互 shell 会卡住（弹 keychain 授权 GUI 对话框）。改用 `printf 'protocol=https\nhost=github.com\n' | git credential fill` 取 password（osxkeychain 已对 git 授权，无感可取）。
- 产物：3 个 zip 上传为 Actions 产物（保留 30 天）；若 secrets.TAURI_SIGNING_PRIVATE_KEY 存在则额外发 GitHub Release `vX.Y.Z` + latest.json（OTA）。thin 版为 x86_64/aarch64，另由 build-release.sh 出 universal。

## 真机日志位置（0.4.4 起）
- 主程序（Rust）：`~/Library/Logs/switchkit-rust.log`
- 守护（Swift）+ 其 stderr：`~/Library/Logs/switchkit-daemon.log`
- 若 daemon 在 exec 瞬间被 AMFI/Gatekeeper 杀：`log show --predicate 'process == "amfid" || process == "syspolicyd"' --last 1h`

## 根因定位（0.4.4 真机日志）—— macOS 27 + Apple 芯片
- 用户环境：**macOS 27 + Apple 芯片**，面板「原生守护」显示「未运行」，但 0.4.4 的 `switchkit-rust.log` / `switchkit-daemon.log` 证明守护**正常 spawn、9876 监听就绪、看门狗已挂父进程**。→ spawn/quarantine/AMFI 假设被证伪。
- 真实根因在状态探测层：`sidecar_status` 用 `{"cmd":"bluetooth:status"}` 判定存活，该命令调 `IOBluetoothHostController.default()/powerState`，在 macOS 27 上可能变慢/挂起（蓝牙权限或 bluetoothd XPC），超过 800ms 读取超时 → 面板误判「未运行」，守护其实活着。
- 日志两个附带 bug：① `switchkit-daemon.log` 每行重复两次（Rust 把子进程 stderr 重定向到该文件，Swift `skLog` 又直接写一遍）；② `strip_quarantine` 日志把 exit 0（已移除隔离）误标成「属性不存在属正常」。

## 修复 0.4.5（已发布 main，run#29 构建中）
- `commands.rs` `sidecar_status`：先 `ping` 判定存活（不碰 IOBluetooth，绝不挂起），再独立探测 `bluetooth:status`（独立连接 + 2500ms 超时，失败仅 bluetooth 置空）。守护活着即显示「运行中」，与蓝牙解耦。
- `bridge.swift` `process`：每条请求记 `recv / dispatch / respond(耗时)`，下次回传日志可确认 bluetooth:status 是否挂起。
- `main.swift` `skLog`：仅写 stderr（由 Rust 重定向落盘），消除重复。
- `main.rs` `strip_quarantine`：日志按真实 exit 标注（exit 0=已移除，exit 1=本就不存在）。
- 两侧编译通过（swiftc + cargo check）。commit `683508c`。
- 构建链接：https://github.com/samjoeyang/unoSwitchKit/actions/runs/41564991594
- 用户机器远程、暂不能跑 CLI；待其装 0.4.5 后看面板是否变「运行中」+ 回传 daemon 日志确认蓝牙耗时。

## 0.4.5 真机验证通过（macOS 27 + Apple 芯片）—— 根因坐实
- 用户装 0.4.5 后面板「原生守护」已点亮。两份日志回传分析确认：
- **实证根因（铁证）**：daemon 日志启动首波请求 `bluetooth:status` 首次耗时 **14468ms**（>=14.5s），`bt:devices` 首次 8743/14471ms；回暖后全部 0ms。`ping` 全程 0ms。
  → 0.4.4 用 `bluetooth:status`（800ms 读超时）判定存活，首个探测卡 14.5s 超时 → 误报「未运行」。守护全程健康。
  → 之前数月的 spawn/quarantine/AMFI 假设是**红鲱鱼**；0.4.4 守护其实每次都正常 spawn，只是状态探测超时。
- **0.4.5 修复验证有效**：ping 存活判定 0ms → 面板立刻点亮；蓝牙状态独立探测 2500ms 超时 → 不拖累存活。
- **附带 bug 修复确认**：日志不再重复落盘（每条仅一次）；`strip_quarantine` 标注正确（本次 exit 1 = 0.4.4 已永久删隔离，属正常）。
- **残留（非阻塞，决定否做 0.4.6）**：bluetoothd XPC 冷启动 ~15s，面板蓝牙状态/设备列表启动后约 15s 内空白，之后填充并保持快速。
  - 优化 A：守护 listen 成功后后台自发一次 `bluetooth:status`/`bt:devices` 空查询预热 bluetoothd。
  - 优化 B：前端蓝牙探测超时保留上一次已知状态而非翻「未知」。
- 结论：核心 bug 已闭环验证。是否做 0.4.6 预热优化待用户决定（先日常用几天看稳定性）。

## 0.4.5 Release 混入旧版本包（0.4.1~0.4.3）的根因与修复
- **现象**：v0.4.5 的 GitHub Release Assets 里出现 0.4.1/0.4.2/0.4.3 的 universal/x86_64/aarch64 zip（非版本号配错，tauri.conf.json/Cargo.toml 都是 0.4.5）。
- **根因**：`build.yml` 用 `actions/cache` 缓存整个 `src-tauri/target`，`restore-keys: macos-cargo-` 前缀匹配会整体恢复历史 target；bundle 目录 `*/release/bundle/macos/` 残留旧版本 zip（脚本只删同名当前版本、不删旧版本）。OTA 发布步骤用通配 `cp src-tauri/target/*/release/bundle/macos/SwitchKit-*.zip ota/` 把残留旧包一并扫进 Release；末尾 `upload-artifact` 同通配也污染 30 天产物。
- **修复**（commit `3c39525`，已本地 commit 未 push）：① 缓存恢复后 `find ... -delete` 清掉残留 SwitchKit-*.zip；② OTA 拷贝与 artifact 上传改为按当前版本+精确架构名拷贝，移除通配。
- **线上已有 v0.4.5 还需手动清理**：`overwrite:true` 只覆盖同名、不删异名旧包，重跑不会清掉 0.4.1~0.4.3。需 GitHub 网页删除这些资产，或装 gh 后 `gh release delete-asset v0.4.5 <name> --yes` 逐个删。
