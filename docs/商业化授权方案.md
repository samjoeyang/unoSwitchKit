# 商业化授权方案（试用期 / 激活码 / 设备数限制）

> 状态：设计稿，**未实施任何代码改动**。对应版本基线 v0.4.1。
> 目标：免费试用 N 天 → 付费获取激活码 → 限制可激活设备数量。

---

## 0. 结论先行

采用**「在线激活 + 离线签名令牌兜底」**三段式，而不是纯离线激活码：

| 环节 | 做法 |
|---|---|
| 试用期 | Rust 侧判定，三处冗余存储 + HMAC 防篡改 + 时钟回拨检测 |
| 激活 | Ed25519 签名令牌；首次激活必须联网，之后 30 天可离线使用 |
| 设备数 | 服务端按 `machine_id` 计数，上限可配（1 / 3 / 无限），支持自助解绑 |
| 兜底 | 客服可为指定机器号签发 90 天离线令牌，邮件发送（应对内网/无法联网用户） |

**为什么不做纯离线激活码**：离线码里若写死 `seats=N`，本地无法知道「已经装了几台」，同一码可无限装；也无法退款吊销。设备数限制这个需求本身就要求一个「能记账的地方」。

**为什么不直接用 Keygen.sh 这类 SaaS**：功能对口（原生支持 device activations + offline license + Tauri engine），但 Std 档 $299/mo、10,000 ALU（[keygen.sh/pricing](https://keygen.sh/pricing/)，抓取于 2026-10-30）；免费 Dev 档仅 100 ALU。对一个 68–128 元级的 Mac 小工具，先自建（成本 < 20 元/月）更划算，等月活过千再考虑迁移。

## 2. 子问题一：试用期 N 天

核心难点不是「记录时间」，而是**防重置**。

### 2.1 存储：三处冗余，取最早值

| 位置 | 路径 | 特点 |
|---|---|---|
| 主记录 | `~/Library/Application Support/com.switchkit.app/trial.json` | 明文可读，便于排障 |
| Keychain | `service=com.switchkit.app, account=trial` | 用户不会主动翻，卸载工具常忽略 |
| UserDefaults | `~/Library/Preferences/com.switchkit.app.plist` | 覆盖面广，重装不触发清理 |

记录结构：

```json
{
  "v": 1,
  "install_id": "uuid",
  "first_run_at": 1761868800,
  "last_seen_at": 1761955200,
  "max_seen_at": 1761955200,
  "hmac": "base32(...)"
}
```

`hmac` = HMAC-SHA256(字段拼接, 编译期密钥)。密钥用 `option_env!` 注入 + 常量拼接派生，**不落盘、不进日志**。

### 2.2 判定规则（按顺序短路）

1. 三处记录全部缺失 → 首次启动，写入并开始计时。
2. 任一记录存在但 HMAC 校验失败 → 判定篡改，直接 `Expired`。
3. 取三处 `first_run_at` 的**最小值**作为起点（防止只改一处就"续命"）。
4. `now < max_seen_at - 5min`（时钟回拨）→ 记 `clock_tampered=true`，**不发放新时长**，按 `max_seen_at` 继续计算。
5. `days_left = trial_days - floor((now - first_run_at) / 86400)`。

### 2.3 残余风险（必须接受）

用户删掉三处记录并重装 → 试用重置。彻底封堵只能在服务端记录「这台机器试用过」，代价是首次启动就要联网，且与「隐私友好」的产品定位冲突。

**建议**：接受这个残余风险。低客单价工具被薅的比例远小于因联网验证流失的正版用户。

## 3. 子问题二：激活码

### 3.1 两种形态

| | A. 纯离线签名码 | B. 在线激活 + 令牌 |
|---|---|---|
| 形态 | `SK1.<payload>.<sig>` 自包含 | 短激活码 + 服务端换 token |
| 服务器 | 不需要 | 需要（轻量） |
| 设备数限制 | ❌ 无法真实执行 | ✅ |
| 退款/吊销 | ❌ 只能靠预置到期 | ✅ |
| 换机 | 需重新出码 | ✅ 自助解绑 |
| 首次联网 | 不需要 | 需要 |
| 破解门槛 | 中（复制码即用） | 中高（token 绑机器） |

### 3.2 推荐：B + 离线令牌兜底

**激活流程**

```
用户付款 → 收到 20 位激活码（如 SWK7-3M9Q-X2HT-8LPD）
   ↓
App「输入激活码」→ 显示本机机器号 A1B2-C3D4-E5F6-7890
   ↓
POST /v1/activate { key, machine_id, app_version, os }
   ↓
服务端：key 有效？已激活数 < seats？
   ├─ 否 → 409 DEVICE_LIMIT + 已激活设备列表（主机名尾号 + 最近心跳）
   └─ 是 → 200 { token: "SK1.<payload>.<sig>", expires_at }
   ↓
App 本地验签 + 校验 machine_id 匹配 → 存 Keychain → 全功能解锁
```

**令牌 payload**

```json
{
  "v": 1,
  "pid": "switchkit",
  "kid": "2026a",
  "plan": "lifetime",
  "seats": 3,
  "mid": "A1B2C3D4E5F67890",
  "iat": 1761868800,
  "exp": 1764460800
}
```

- 签名：Ed25519，私钥只在服务端；公钥 `SWITCHKIT_LICENSE_PUBKEY` 编译期注入。
- `exp` = 签发 + 30 天。App 每次启动先验签，再检查 `exp` 与 `mid`。
- 续期：启动时或每 7 天尝试 `/v1/heartbeat`；**失败不阻塞使用**，只用本地令牌。
- 令牌过期且联网失败 → 进入 `Grace` 宽限 7 天（只读提醒），再失败 → `Locked`。

这个设计的关键点：**令牌本身是自包含且签名的**，所以服务端挂了、用户断网、公司内网，都不影响已激活用户。服务器只承担「计数」和「签发」两个职责，不在关键路径上。

## 4. 子问题三：设备数限制

### 4.1 机器号生成

```
raw = IOPlatformUUID          # ioreg -rd1 -c IOPlatformExpertDevice
    + hw.model                # 如 Mac14,2
mid = base32(sha256("switchkit/v1|" + raw))[0..16]  → 展示为 A1B2-C3D4-E5F6-7890
```

- `IOPlatformUUID` 重装系统不变，换逻辑板会变（语义正确：换主板 = 换机器）。
- **不用 MAC 地址**：会变，Wi-Fi 关闭时取不到。
- **哈希加盐**：不把原始硬件 ID 外传，符合最小化原则。

### 4.2 服务端数据结构

```sql
licenses(key PK, plan, seats, status, order_id, email, created_at, note)
activations(id PK, license_key, machine_id, hostname, os_ver,
            first_seen, last_seen, revoked_at)
-- 唯一约束：(license_key, machine_id) WHERE revoked_at IS NULL
```

### 4.3 计数规则

| 规则 | 说明 |
|---|---|
| 激活准入 | `count(active) < seats` 才通过 |
| 释放 | 心跳更新 `last_seen`；> 90 天无心跳的激活可自动回收名额 |
| 自助解绑 | 每 30 天 3 次；App 内可解绑自己，网页端可解绑任意旧机 |
| 超限响应 | 返回 `409` + 设备列表（`MacBook Pro · 尾号 7Q` + 最后活跃日期），引导用户自己腾位置 |
| 吊销 | 退款/拒付时 `status=revoked`，下次心跳即失效 |

名额回收这一步很关键：用户换电脑时**不需要联系客服**，这是留存差异点。

## 5. 状态机

```
Fresh ──首次启动──> Trial ──到期──> Expired ──激活──> Active
                      │                                  │
                      └──激活──> Active                  ├─ 令牌过期+断网 ──> Grace(7d 只读) ──> Locked
                                                         └─ 吊销/超限 ──────> Locked
```

| 状态 | 面板表现 | 写操作 |
|---|---|---|
| `Trial` | 底部「试用剩余 N 天」 | 放行 |
| `TrialExpiring`（≤3 天） | 顶部黄色横幅 + 购买入口 | 放行 |
| `Expired` | 顶部横幅 + 遮罩引导激活 | **拦截** |
| `Active` | 无提示（安静） | 放行 |
| `Grace` | 「已离线 X 天，请联网校验」 | 放行 |
| `Locked` | 全屏激活页 | 拦截 |

## 7. 代码接入点（设计，不实施）

### 7.1 新增 Rust 模块

```
src-tauri/src/license/
├── mod.rs      # LicenseState 枚举 + 启动时计算快照，manage 进 AppState
├── machine.rs  # machine_id（ioreg + hash + base32）
├── trial.rs    # 三处存储读写、HMAC、时钟回拨检测
├── token.rs    # Ed25519 验签、payload 解析（ed25519-dalek）
├── api.rs      # activate / heartbeat（reqwest，复用 settings.http_proxy）
└── guard.rs    # require_write() -> Result<(), LicenseError>
```

新增依赖：`ed25519-dalek`、`base32`、`keyring`、`reqwest`（`rustls-tls`，避免 OpenSSL 体积）。

### 7.2 命令层门控

原则：**只读命令不加门，写命令全加门**。

- 不加门：`get_toggle_states`、`get_settings`、`sidecar_status`、`bt_devices`、`get_balances`
- 加门：其余 20 个写操作（`toggle_*`、`empty_trash`、`release_memory`、`flush_dns`、`clear_cache`、`lock_screen` 等）

实现方式建议用宏收口，避免 20 处手写 `if`：

```rust
macro_rules! gated {
    ($app:expr, $body:block) => {{
        crate::license::guard::require_write($app)?;
        $body
    }};
}
```

理由：逐命令散写容易在后续加功能时漏掉，形成一个洞。

新增命令：

| 命令 | 作用 |
|---|---|
| `license_status` | 返回状态、剩余天数、机器号、席位使用情况 |
| `license_activate(key)` | 联网激活 |
| `license_heartbeat` | 续期（失败静默） |
| `license_deactivate_local` | 本机解绑（清缓存） |

### 7.3 前端

- `src/components/LicenseBanner.tsx`：顶部横幅（试用剩余 / 已到期）
- `src/components/LicenseGate.tsx`：激活页（机器号一键复制 + 激活码输入 + 购买链接）
- `src/components/LicenseSection.tsx`：设置内状态行（版本、席位、解绑）
- `App.tsx`：启动拉 `license_status`，状态决定是否渲染 Gate

**前端只做 UX，Rust 是唯一权威**。理由：WKWebView 的 JS 环境可被开发者工具或注入脚本影响，任何只在前端执行的判断都等于没有。

### 7.4 编译期配置（沿用现有 `SWITCHKIT_UPDATE_ENDPOINTS` 模式）

| 变量 | 用途 |
|---|---|
| `SWITCHKIT_LICENSE_API` | 激活服务基址 |
| `SWITCHKIT_LICENSE_PUBKEY` | Ed25519 公钥 base64 |
| `SWITCHKIT_TRIAL_DAYS` | 试用天数（默认 14） |

## 8. 服务端（最小可用）

**技术选型**：Cloudflare Workers + D1（SQLite）。免费额度对千级用户足够，无运维，国内访问延迟可接受。备选：Fly.io / Railway + SQLite，或腾讯云函数 + MySQL（若需备案域名）。

| 端点 | 说明 |
|---|---|
| `POST /v1/activate` | key + machine_id → 签名令牌 |
| `POST /v1/heartbeat` | 令牌 → 续期新令牌，更新 last_seen |
| `POST /v1/deactivate` | 解绑指定 machine_id |
| `GET /v1/health` | 探活 |
| `POST /webhook/payment` | 支付成功 → 生成 key → 发邮件 |

发码策略：MVP 阶段**手工发码**即可（支付后台看到订单 → 跑一条 CLI 生成 key → 邮件）。订单量到日均 5 单再上 webhook 自动化。

| 渠道 | 大陆个人主体 | 费率 | 备注 |

## 10. 到期后的降级策略（产品决策，建议）

| 策略 | 说明 | 风险 |
|---|---|---|
| 硬锁 | 整个面板替换为激活页 | 菜单栏工具的价值就是「一键」，硬锁 → 直接卸载 |
| **软锁（推荐）** | 保留状态展示与只读，写操作拦截并弹激活提示 | 转化路径最短 |
| 免费版分级 | 保留 3 个基础开关，Pro 解锁资源释放/蓝牙/余额 | 长期留存最好，但改造量最大 |

软锁的收益在于：用户每天看到图标 → 每天被提醒一次 → 但没被剥夺「查看」的权利，卸载冲动低得多。

## 11. 防破解的现实边界

**能做到**
- Rust 侧判定，前端资源内嵌二进制（改 UI 需 patch Mach-O）
- 令牌绑定 `machine_id`，复制到另一台机器直接失效
- 已有 strip + LTO，符号信息少
- 代码签名 + 公证后，用户改签名会破坏公证，重打包分发成本上升

**做不到**
- 有决心的人 patch 掉 `require_write` 的返回值 → 必然可行，只是成本问题
- 从 Keychain 提取令牌

**建议**：不做反调试、不加壳、不做代码混淆。目标定为「让 90% 的正常用户顺利付费」，而不是「100% 防住」。对抗强度越高，误伤正版用户和维护成本越大，对 68–128 元的产品完全不划算。

## 12. 分期计划

| 阶段 | 内容 | 预估 |

| M1 | 试用期（trial.rs + license_status + 横幅/Gate 骨架） | 0.5–1 天 |

M1 结束即可内测验证「判定是否可靠」；M2 结束可真实收款。**公证（notarization）应并入 M4 之前的发布清单**，与授权无关但直接决定付费转化。
